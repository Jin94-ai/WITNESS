리팩토링을 제안합니다.

대상: $ARGUMENTS

## 사전 확인 (Feedforward)

1. 대상 파일을 읽어 현재 구조와 의존성을 파악한다
2. 관련 테스트 파일이 있는지 확인한다 (테스트 없는 대규모 리팩토링은 위험 경고 필수)
3. 리팩토링 범위를 명확히 한다 — 요청되지 않은 파일은 건드리지 않는다

## 분석 항목

1. **코드 스멜** — 긴 함수(50줄+), 중복 코드, 복잡한 조건문, God 클래스
2. **구조 문제** — 높은 결합도, 낮은 응집도, 순환 의존성
3. **개선 기회** — Extract Function/Class, 중복 제거, 조건 단순화

## 리팩토링 원칙

- **동작 변경 없이 구조만 개선** — 기능 추가는 별도 작업
- 한 번에 하나의 패턴만 적용
- 각 단계 후 테스트 실행 가능하게 분리

## 출력 형식

```markdown
## 현재 문제점
[문제 목록 + 영향]

## 리팩토링 계획

### Step 1: [작업명]
- 패턴: [적용 패턴]
- 이유: [이유]
- Before/After 코드

### Step 2: ...

## 예상 개선
- 가독성: 향상 내용
- 복잡도: 감소 내용
```

## 자가 체크 (Feedback)

- [ ] 모든 변경이 동작을 보존하는가?
- [ ] 요청 범위 외 파일을 수정하지 않았는가?
- [ ] 각 단계가 독립적으로 테스트 가능한가?
- [ ] 테스트 없는 코드의 대규모 변경에 위험 경고를 포함했는가?
